# Архитектура системы: Wildberries AI Assistant

## 1. Архитектурный паттерн: Onion Architecture (Луковичная архитектура)
Система строится по принципу чистой архитектуры для обеспечения независимости бизнес-логики от внешних инструментов и легкости тестирования.

### Слои системы:
1.  **Core (Domain Layer):**
    * Содержит сущности бизнеса: `Seller`, `Shop`, `Order`, `Product`, `Report`.
    * Интерфейсы репозиториев и сервисов.
    * Логика расчета юнит-экономики (маржинальность, КВВ, логистика).
2.  **Application Layer:**
    * Сценарии использования (Use Cases).
    * Оркестрация ИИ-агентов через `CrewAI`.
    * Обработка команд и запросов (CQRS Lite).
3.  **Infrastructure Layer:**
    * Реализация работы с БД (SQLAlchemy репозитории).
    * Интеграция с Wildberries API (обработка лимитов, авторизация через OAuth 2.0).
    * Интеграция с Redis, Celery и LLM провайдерами.
4.  **Presentation Layer:**
    * FastAPI маршруты (REST API).
    * Взаимодействие с Next.js UI.

## 2. Мультиагентная система (AI Engine)
Ядро интеллекта приложения базируется на разделении обязанностей между специализированными агентами:

* **Chief Orchestrator:** Принимает запрос пользователя, анализирует контекст (текущий дашборд) и ставит задачи под-агентам.
* **Data Fetcher:** Отвечает за получение актуальных срезов данных из PostgreSQL или напрямую из WB API (если кэш протух).
* **Financial Analyst:** Анализирует отчеты о реализации (`reportDetailByPeriod`), находит аномалии в комиссиях или штрафах.
* **Warehouse Analyst:** Следит за оборачиваемостью, лимитами складов и рисками блокировки товаров.
* **Report Generator:** Формирует финальный текстовый ответ и рекомендации для пользователя.

## 3. Интеграция с Wildberries API: Стратегия отказоустойчивости
На основе актуальной документации WB API, реализованы следующие механизмы:

* **Rate-Limiting Manager:** Внедрение алгоритма *Exponential Backoff with Jitter* для обработки ошибок `429 Too Many Requests`.
* **Metadata Validation:** Превентивная проверка IMEI (15 цифр), КИЗ и УИН на стороне клиента для исключения ошибок `409 Conflict`, которые «штрафуют» лимиты запросов на стороне WB.
* **Source of Truth:** Использование метода `reportDetailByPeriod` как единственного источника для финансовых сверок, учитывая задержки асинхронной репликации в WB (до 24 часов).
* **Service Secrets:** Обязательное использование заголовка `X-Client-Secret` для изоляции квот запросов в рамках нашего приложения.

## 4. Контур безопасности
* **Database RLS:** Каждый SQL-запрос автоматически фильтруется по `seller_id`, гарантируя, что один пользователь никогда не получит доступ к данным другого.
* **Secret Management:** API-ключи селлеров хранятся в зашифрованном виде в базе данных PostgreSQL.
